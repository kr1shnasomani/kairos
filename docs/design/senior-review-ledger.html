The landing page changed underneath this work resolved in favour of main

While this pass was in progress, main shipped a full landing-page redesign — the one now live at kairos-deterium.vercel.app. It wins outright.

What was discarded, and why

Task D6 had added 39 reveal wrappers and roughly 29 md: classes to the old landing page — a page that no longer exists. All of it is gone. Main's version is byte-identical in this branch.

The tablet gap it was fixing is still real, just on a different page: main's landing measures 74 sm:, 36 lg:, and zero md:, so every viewport between 768 and 1023px still renders a stretched small-screen layout. Carried into the visual identity pass.

A clean auto-merge is not a correct auto-merge

page.test.tsx merged with no conflict markers at all — and was still wrong. It kept assertions for a landing-reveal testid that main's page does not contain. Green merge, red suite. Overridden with main's version.

globals.css did merge correctly, and this was verified at line level rather than by grepping for strings: 42 of 42 lines main added and 53 of 53 this branch added are present, with zero collisions. The two sides appended to different regions — main the landing motion, this branch the app tokens and nav rail.

The drift marker fired, exactly as designed

landing-figures.test.ts carried an it.fails() marker while the landing showed 34/37 against the benchmark's 33/37. It was built to start failing the moment the two agreed — and it did. Main's landing reads 33/37 at 89%, matching RESULTS.md.

The marker is gone and the test now passes normally. Worth flagging: the 91% figure chosen for the demo is no longer on the page. Main went with the honest number.

Two corrections to my own record

The senior was right about item 4; I was not

I recorded the Y-axis labels as absent, from a selector returning zero. That selector (.recharts-yAxis .recharts-cartesian-axis-tick-value) can never match in this Recharts version — the tick text is a sibling of the axis layer, not a descendant. An agent caught it and said so.

Measuring both builds settled it: the ticks were always there, sitting 2px from the card edge inside its 16px padding. Clipped, exactly as the review said. Now 26px.

And a third time, on the events legend

I reported the legend swatches as black. I had sampled the first <path> inside each legend item, which is not the swatch. The real icons are .recharts-legend-icon, and they render red and amber — matching their bars.

Three wrong readings in one project, all the same shape: a selector that matched the wrong node or nothing at all. Each one nearly closed an item that was broken, or reopened one that was already right.

A query returning zero is not evidence of absence

This is the second time in one project. The first cost more: an audit counted five <th> elements on /assets, declared three review items already fixed, and was wrong — the columns were rendering at 0px. Six tables shipped one visible column.

Both failures share a shape: a false "already fixed" sends work in the wrong direction and stays invisible until someone opens the page. Confirming a defect is absent deserves more scepticism than confirming it is present.
